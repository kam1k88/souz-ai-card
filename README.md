# AI-помощник для карточек товаров (тестовое задание «Союз-Прибор»)

Прототип: по данным о контрольно-измерительном приборе (JSON) через LLM API формирует черновик
карточки для B2B-магазина: SEO-заголовок, SEO-описание, характеристики, поисковые запросы и
commercial-блок для менеджера. Если данных не хватает, явно пишет «данных нет».

## Быстрый старт

Нужен Python 3.10+.

### Вариант 1: Облачный API (Groq) — быстрый запуск
Для тестирования использовалась бесплатная модель `openai/gpt-oss-120b` через API Groq.

1. Установите зависимости:
   ```powershell
   python -m venv .venv
   .venv\Scripts\activate
   pip install -r requirements.txt
   pip install openai
   copy .env.example .env
   ```
2. В файле `.env` укажите ключ Groq (можно получить бесплатно на console.groq.com):
   ```env
   LLM_PROVIDER=openai
   OPENAI_API_KEY=ваш_ключ_gsk_...
   OPENAI_BASE_URL=https://api.groq.com/openai/v1
   LLM_MODEL=openai/gpt-oss-120b

### Вариант 2: Локальный запуск (Ollama) — без интернета и ключей
1. Установите [Ollama](https://ollama.com/download) и скачайте модель:
   ```bash
   ollama pull qwen2.5:7b-instruct
   ```
2. Установите зависимости проекта (как в Варианте 1) и укажите в `.env`:
   ```env
   LLM_PROVIDER=ollama
   LLM_MODEL=qwen2.5:7b-instruct
   OLLAMA_HOST=http://localhost:11434
   ```

### Запуск
```bash
# 1. Товар из JSON-файла
python main.py examples/demo_input.json

# 2. Товары из фида: посмотреть список, сохранить нужный в JSON, сгенерировать
python main.py --feed https://www.souz-pribor.ru/yml/any/feed.xml --list
python main.py --feed https://www.souz-pribor.ru/yml/any/feed.xml --offer-id <ID> --save-input examples/product_1.json
python main.py examples/product_1.json
```

Результат печатается в консоль (Markdown) и сохраняется в `out/<товар>.md` и `out/<товар>.json`.

## Принятые решения

**Борьба с выдуманными характеристиками: три уровня.**
1. *Промпт.* В system-части жёсткие правила: единственный источник фактов — входной JSON, числа
   и единицы только из входа, отсутствующее перечислять в `missing_data` как «данных нет».
   Входные данные явно объявлены данными, а не инструкциями. Температура 0,2.
2. *Архитектура.* Таблицу характеристик собирает код напрямую из `specs`: модель её не пишет и не
   может исказить. Пустые значения помечаются «данных нет». Модель отвечает только за тексты.
3. *Пост-проверка.* Код находит в сгенерированных текстах числа, которых нет во входных данных,
   и выводит предупреждение для контент-менеджера (`unverified_numbers`).

**Структурированный ответ.** Модель возвращает один JSON по схеме. Парсер терпим к обрамлению
(```json) и мусору вокруг, но схема проверяется строго.

**Автоповтор вместо слепого доверия.** Модели плохо считают символы, поэтому длины
(заголовок ≤ 70, описание 800–1200, 3–5 запросов) проверяются кодом. При нарушении или
невалидном JSON делается до 3 попыток, и в повторный запрос добавляется, что именно исправить.
Если после всех попыток длина не в норме, результат не скрывается, а выдаётся с предупреждением.

**Обработка входа до обращения к API** (экономит деньги и даёт понятную ошибку):
битый JSON, не объект, нет `name`, нет ни `specs`, ни `description`. Пустые отдельные поля не
блокируют генерацию, а попадают в раздел «Требует уточнения».

**API-ключ** (для облачных провайдеров) читается только из переменных окружения / `.env` (он в `.gitignore`), в коде ключей нет.

## Ограничения

- Нет проверки смысла: «лишние числа» ловятся, а нефактические выдумки (например, область применения,
  не следующая из описания) проверяются только промптом и глазами менеджера.
- Проверка чисел простая: она не понимает пересчёты единиц (МПа → бар) и может дать ложное срабатывание.
- Фид парсится по стандартному YML (`name`, `vendor`, `description`, `param`). Нестандартные поля
  фида не учитываются. Из описания вырезается HTML.
- SEO-запросы строятся только по входным данным, без анализа реального спроса (Wordstat и т. п.).
- Один товар за запуск, без очереди, кэша и учёта стоимости.
- Небольшие локальные модели (3–8 млрд параметров) слабее облачных: чаще нарушают длину и могут допускать
  неточности в русском. Это компенсируется повторными запросами и пост-проверками, но для продакшена
  лучше использовать облачный API (например, Groq).
- Качество зависит от полноты входных данных: при скудном описании текст получится общим.

## Возможные улучшения

- Режим пакетной обработки всего фида, кэш результатов.
- Нативный structured output / tool use провайдера вместо разбора JSON из текста.
- Нормализация единиц и более точная проверка фактов (сопоставление значений со `specs`).
- Веб-форма (FastAPI/Streamlit) с кнопкой «копировать» и подсветкой предупреждений.
- Подбор запросов по реальной частотности, проверка уникальности текста.
- Оценочный набор (golden set) из эталонных карточек для регрессионной проверки промпта.
- Логирование стоимости и токенов.
